# Works tools reach agents through a CLI, with MCP only where policy allows

Company managed policy on the developer's machine blocks injected MCP servers (stdio, http and sse were all refused under `claude -p`), so the tools ADRs 0001 and 0004 assumed would arrive over MCP are delivered another way. The Works defines one tool API (for the Archwright: the Guild and Jig catalogue, Jobs, Plans, findings, tasks and the inbox; for Wardens: `dispatch_wright`, inspection and handback; for Wrights: reporting a result), and agents call it through the `archwright tool <name>` CLI with JSON in and out, run through Bash, which works under any policy. An MCP shim over the same API is used only where policy permits it, and asking the admins to allowlist a Works MCP server is optional and not a dependency. Skills and brief templates tell agents to call the CLI. ADRs 0001, 0002 and 0004 are amended accordingly.

The developer allows `archwright tool` to run without a prompt once, in their own settings; `archwright doctor` probes each runner and prints the exact rule needed, runs refuse to start visibly until it passes, and the factory never adds the rule or an auto-approve hook for its own command (ADR 0011). Each run gets its run id, spool path and a scoped single-run token through environment variables set when the Works spawns it, and the Works authorizes every call by role (ADR 0018 amends this: both runners passed such variables through in testing, so no context file is needed in the working directory). Hooks supplied through `--settings` run under the observed policy, and are used only for the Archwright's inbox of dashboard commands and for recording posture, never for permissions or tool delivery; if hooks are blocked, the Archwright polls the inbox with the CLI. The transport between the CLI and the Works is a file spool in each runner's temp area (ADR 0018).
