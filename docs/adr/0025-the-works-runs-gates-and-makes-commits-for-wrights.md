# The Works runs gates and makes commits for Wrights

Under the developer's managed policy a Wright cannot run the Site's checks: the managed Bash allow list has no `go` or `make`, user and project allow rules are ignored (`allowManagedPermissionRulesOnly`), and Go's default build cache is outside the sandbox's writable paths, so even `make check` is denied (issue #112, live shakedown #88). Both Wright rounds returned `blocked`, as ADR 0011 requires, with nothing committed. A writable `GOCACHE` would not help, and the Works may not add allow rules, so instead of widening what the Wright can run, the Works runs the checks for it, as ADR 0022 already does for Forge actions.

Wrights get a `run_gate` tool, called through `archwright tool` like every other Works tool (ADR 0014, ADR 0018). It takes at most a registered gate name (`test`, `lint`, `vet`, and so on) and runs every gate when none is given; no free arguments and no test filters, because the Works runs the result outside any agent sandbox, as the developer. The Works takes a snapshot of the Wright's worktree, tracked and untracked files, into a throwaway checkout and runs the Site's registry gates there (ADR 0010), the same isolation handback gates have, so a gate can never write into the Wright's tree or its git directory. Calls are bounded by the existing gate timeout, one run at a time per Job, and a per-dispatch cap (a Works default, not a Guild setting). Claude and Codex Wrights both use it, and the masonry standards tell them to, instead of running go or make themselves. The handback gate run (ADR 0010) is unchanged and remains the authoritative check; `run_gate` is the Wright's own early look.

The Wright no longer commits. When it reports, whether done, blocked or failed, the Works commits its worktree to the piece branch (marked as work in progress when the Wright did not finish), so the Wright needs no git write access and a rework round can continue from what the last round did (issue #113) (ADR 0022 had assumed a sandboxed Wright could `git commit` in a Works worktree; whether policy allows it was never verified, and this removes the dependence). The Works decides what is staged and keeps run scaffolding such as `.agents/` and `.claude/` out of the commit.

When the Warden accepts a piece, the Works merges, or fast-forwards, the piece branch into the Job's integration branch, the branch the gates, the push and the PR use; a conflict becomes a merge Wright task. ADR 0008 had a merge Wright do this for every piece, but no such step existed, and a merge Wright for what is usually a trivial merge is a full agent run for no gain.

This amends ADR 0008 (the Works merges accepted pieces itself), ADR 0011 (a Wright's checks no longer need an allow rule, so the denial that blocked the shakedown cannot arise for them) and ADR 0022 (the Works also runs gates and makes commits for Wrights; both stay local to the machine). It does not widen any permission: the Works already runs gate commands as the developer (ADR 0010), and now also runs them earlier, when asked, from a role-checked Wright of the Job. The cost is a slower test-first loop, since a Wright runs a whole gate, not one test.
