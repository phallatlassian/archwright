# Tool calls travel through a spool in each runner's temp area, and factory skills stay out of git

Tests from inside the runner sandboxes showed that loopback HTTP reached the Works only under Codex, Unix sockets failed in both runners, and a developer-home path outside the working directory was not writable from either; the one location outside the working directory that both runners could write was each runner's own temp directory (Claude `-p`: `/tmp/claude-<uid>`; Codex: its `$TMPDIR`). So `archwright tool` calls travel as files: the CLI writes a request file into a per-run spool directory (under a temporary name, then renamed so it appears whole) and waits for the matching response file, and the Works watches the spool directories of runs it started (file events plus a periodic scan) and answers the same way. The adapter picks each runner's spool root, the Works creates it mode 0700 before the run starts, and the run learns where it is through environment variables set at spawn (`ARCHWRIGHT_RUN`, `ARCHWRIGHT_SPOOL`, `ARCHWRIGHT_RUN_TOKEN`), which both runners passed through to shell commands in testing; nothing about the transport sits in the working directory. Each request has a unique id and is idempotent by it, responses are never overwritten, calls are short and synchronous with a 60-second wait before the CLI exits with a distinct code and the run reports failed (`works_unreachable`), `ask` returns at once with the ask id (waiting is parking, ADR 0015), and the Works removes processed files and the run's spool when the run ends. Every request is untrusted input: the Works reads only the spool of runs it started, checks the request's single-run token against that run's role, validates the schema and authorizes by role and run state, so a prompt-injected agent can do only what its role already permits. This amends ADR 0014.

Factory skills are delivered the same way to both runners and add nothing to the Site's repository. The Works writes a per-run copy of the Guild's skills into `.agents/skills` in the run's worktree, which is the location Codex scans. Claude Code does not read `.agents/skills` (tested: the skill was absent), so for Claude runs the Works also creates `.claude/skills` as a symlink to `../.agents/skills` (tested: the skill is then present, under its plain name); if the Site already has a `.claude/skills` directory, the Works adds one symlink per skill inside it instead, and never overwrites a skill the Site tracks (a name collision fails the run visibly). Both locations are hidden from git for the run without any change to the repository: the Works generates a git configuration file for the run, points `GIT_CONFIG_GLOBAL` at it, and that file includes the developer's own global git configuration and then sets `core.excludesFile` to a Works-generated excludes file that carries the developer's own global excludes plus exactly the paths the Works created. Every git command the run executes inherits it, so `git status` is clean and `git add -A` stages nothing; the Site's `.gitignore`, `.git/config`, `.git/info/exclude` and tracked files are never touched, and the handback diff check remains a backstop. `GIT_CONFIG_GLOBAL` is used rather than git's `GIT_CONFIG_COUNT` variables because Claude Code sets its own `GIT_CONFIG_COUNT` and key entries in the shells it runs, which defeated the exclusion in testing; `GIT_CONFIG_GLOBAL` worked inside both Claude and Codex runs. This amends ADR 0005. The per-user directory of ADR 0016 is split in the XDG style: configuration the developer edits (`config.toml`, `guilds/<name>/`, `jigs/`) in `~/.config/archwright`, and state the Works generates (the SQLite database, logs, worktrees and per-run generated files such as the git configuration and excludes files) in `~/.local/state/archwright`, both mode 0700, honouring `XDG_CONFIG_HOME` and `XDG_STATE_HOME` and overridable by `ARCHWRIGHT_CONFIG_HOME` and `ARCHWRIGHT_STATE_HOME`.
