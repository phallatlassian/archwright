# One Go binary, built locally, started on demand

The factory is a single Go executable, `archwright`, that is the CLI, the Works daemon, the `archwright tool` shim, `archwright doctor` and the dashboard server (static web assets embedded), with a pure-Go SQLite driver. Go fits the Works' work (spawning runner processes, watching files, HTTP and SSE, SQLite), matches the developer's existing `otman`, and leaves no runtime or dependency tree to keep in step; a Node/TypeScript build was rejected for that reason. It is built from source on the developer's machine from the factory repository into a per-user bin directory, with no prebuilt binaries and no auto-update in v1, because managed endpoints may block downloaded unsigned executables and this is a single-developer tool. Upgrading is pull, rebuild, `archwright upgrade`.

The Works starts on demand: any command that needs it starts it detached when it is not running, with a single-instance lock and pid file in the state directory recording its loopback port and token. It keeps running so Jobs outlive the Archwright session, until `archwright stop` or a reboot, and the next command restarts it and recovers per ADR 0002; there is no launchd agent in v1. The per-user data is split in the XDG style (ADR 0018 amends this): configuration the developer edits (`config.toml`, `guilds/`, `jigs/`) in `~/.config/archwright`, and state the Works generates (the database, logs, the Works' clones of each Site, worktrees, per-run generated files) in `~/.local/state/archwright`, both mode 0700. Shipped Guilds, Jigs and vendored skills are embedded in the binary and materialized per run, so a rebuild upgrades them and user overrides are untouched; SQLite migrations are forward-only and automatic at Works start after copying the database aside, and a binary refuses to open a newer schema. `archwright upgrade` refuses to restart the Works while runs are active unless the developer confirms. `archwright doctor` is read-only and prints the exact fix for anything it finds: runner presence and versions, managed-policy notices per runner, whether `archwright tool` runs unprompted in each runner, each Site's repository, Pocock configuration and gate commands, data directory permissions and schema version, Works reachability and port, and tool transport from inside each runner's sandbox.
