# Guilds and Jigs are local file definitions; a Guild can only narrow permissions

A Guild is a directory: `GUILD.md` (YAML frontmatter manifest naming its intake, handback, default runner and permitted set, required capabilities, access, rework limit and skills; body holding the charter and standards), `warden/SKILL.md`, and optional `wrights/<kind>.md` brief templates, following the same convention as the skills so agents and humans read it alike. A Jig is one YAML file (name, description for the Archwright to choose it, parameters, and steps with id, Guild, task template, inputs and outputs, blocked_by and a human-checkpoint flag), validated against the loaded Guild catalogue. We rejected code plugins because adding a Guild must not change the daemon.

Definitions ship with the factory read-only and are added or overridden in a per-user directory; the same name replaces the shipped one entirely, with no merging. They load at Works start and on an explicit reload, fail closed (an invalid definition is not loaded, the previous good one stays, the error shows on the dashboard), and are only ever read from local files. A Guild may declare read-only or read-write access and extra denied tools, which adapters turn into runner restrictions (read-only Guilds also get detached worktrees), but it can never grant beyond the developer's own runner configuration and managed settings; a restriction the runner cannot enforce fails the capability check. Chancery, Engineering, Research and Review ship as ordinary definitions with no privileged code, the Archwright learns the roster from a Works catalogue tool, and only the developer creates Guilds: if none fits a Job, the Archwright says so.
