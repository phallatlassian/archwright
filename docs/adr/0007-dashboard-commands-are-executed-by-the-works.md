# Dashboard commands that are mechanical are executed by the Works, not relayed through the Archwright

The dashboard is a control surface, but the Archwright is a stock interactive session that only sees input at turn boundaries (ADR 0001), so routing every click through it would make cancel lag by a turn. Every command is recorded as an event first. Mechanical state transitions (cancel a Job or Wright, pause and resume, approve or reject a Plan, answer a pending ask) are executed by the Works immediately and reported to the Archwright; commands that need judgment (a free-text instruction, retry with new instructions, re-plan, change a Jig) are delivered to the Archwright's inbox. The Archwright remains the only conversational voice, and the dashboard has no direct line to Guilds.

The Works serves an HTTP API and a one-way SSE stream with cursor replay from the SQLite events table (ADR 0002), with commands as separate POSTs. It binds to the loopback interface only, requires a per-install token on every request (handed to the browser by the `archwright` CLI), and rejects cross-origin command requests; there is no remote access in v1. The Works keeps full event content locally in its per-user SQLite with user-only file permissions and never sends it elsewhere, which is what lets the run drill-down show any run's timeline read-only. The dashboard's static pages, which carry no data and no secret, are the one thing served without the token (a browser cannot send a header on navigation); the page takes the token from the URL fragment, which is never sent to the server, and presents it on every API call.
