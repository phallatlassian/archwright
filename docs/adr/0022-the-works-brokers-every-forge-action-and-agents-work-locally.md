# The Works brokers every Forge action; agents work locally only

Runs are sandboxed, and under the developer's managed policy the sandbox defeats anything that needs the network or the developer's credentials: `gh` fails TLS verification under macOS Seatbelt (issue #73), the retry outside the sandbox is denied when headless, and `git push` or `gh pr create` would fail the same way. ADR 0008 assumed the Warden could push and open the PR "under the runner's normal permission rules"; on a managed machine it cannot, and a pipe or a heredoc in the command makes denial more likely still. Briefing around it (putting issue text in the Brief) fixes one symptom and leaves push, PR and comments broken, so the Works, which is unsandboxed and holds the developer's credentials, performs every Forge action itself.

The Forge is the service that hosts a Site's repository, issues and pull requests (GitHub today). Agents never run `gh` or `git push`. They call Forge tools through `archwright tool` (ADR 0014, ADR 0018), and the Works authorizes each call by role, run token and run state like any other tool. Every target is resolved from the Job, never from an argument, so a prompt-injected agent can reach only what its role already permits:

- **Issue read** (Warden and Wright): returns the Job's own source issue and takes no issue number; the text is labelled untrusted. A Job without an issue gets a clear "no source issue" result.
- **Push** (Warden): pushes the Job's integration branch from the Works' own clone, never forced and never the Site's default branch. Allowed during the `open-pr` step and again while the Job's PR is open (conflict and review fixes); nothing leaves the machine before review passes (ADR 0012).
- **PR open** (Warden): the Warden supplies title and body; the Works fixes head (the integration branch) and base (the Site's base branch). One PR per Job; calling again returns the existing PR.
- **PR read and PR comment** (Warden): the Job's PR only; reads include CI check status.

Merge conflicts with the base branch are resolved by a Wright merging the base into the integration branch and the Works pushing the new commits as a fast-forward, so no force push is ever needed. The Warden's `merge_base` tool does this: it takes no argument, has `read_pr` confirm the conflict, has the Works fetch the base into its own clone, and dispatches a merge Wright into the Job's integration worktree, so the merge commit lands on the integration branch itself; the Warden accepts it and calls `push_branch`, which refuses, before reaching the Forge, a branch that no longer contains what was last pushed. The `merge-base-` piece prefix is reserved to `merge_base`: `dispatch_wright` and `rework_wright` reject it, so no Warden-briefed Wright can run in the integration worktree. The adapter shells out to the developer's own `gh` behind a Forge seam, reusing stored credentials and keeping any secret out of Archwright's configuration; a second Forge would be a second adapter. A Forge call that fails returns a structured error to the agent and, for authentication or network faults, raises a Needs-you entry; there is no automatic retry. A Site on a host with no adapter is still allowed: Forge tools answer "unsupported", and at `open-pr` the step fails visibly as a Needs-you entry with the integration branch kept for the developer to push. `archwright doctor` checks that `gh` is installed and authenticated and that the tool transport works, and prints the remedy without applying it.

The `pr` skill is forked so its create-PR step calls the Forge tool (ADR 0005), and the Warden and Wright prompts tell agents to use the Forge tools and never `gh` or `git push`, and to run one simple command per Bash call, with no pipes, heredocs, `cd` or command substitution, because under the managed policy a compound command is allowed only if every part is. That guidance is soft mitigation, not a boundary.

Local commits remain the agent's own work, which assumes a sandboxed Wright can `git commit` in a Works worktree whose git directory sits outside the working directory. Claude's documentation says a linked worktree's shared git directory is writable; our clone is bare and Codex is undocumented, so this is untested. A gating spike checks it, together with whether `archwright tool` is approved under `dontAsk` as well as `default`, and that the Works can run `gh` outside the sandbox. If a Wright cannot commit, the Works brokers a `commit` tool in the same way rather than widening runner permissions. (Superseded by ADR 0023: Codex Wrights commit under `workspace-write` with Works-computed writable roots; no `commit` tool.)

This amends ADR 0008 (the Warden no longer pushes or opens the PR itself; the Works does at the Warden's request) and ADR 0014 (adds the Forge tools to the catalogue). It is consistent with ADR 0011: brokering widens no runner permission, because the Works acts only within what the caller's role permits and the guard on `--add-dir`, `--sandbox`, `-c` and settings writes is unchanged. Build commands that managed policy also blocks (`pnpm`, `go test`, dependency installs, Codex network access) are out of scope here.

Amended by ADR 0025: the Works also runs gates and commits for Wrights; the assumption above that a sandboxed Wright can `git commit` no longer applies.
